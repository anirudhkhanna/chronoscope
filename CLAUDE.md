# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

⏱️ Chronoscope — webpage latency testing kit. It drives a real, locally installed Chrome via Playwright to repeatedly hit a configured set of URLs, reads timing straight from the Navigation Timing API (the same numbers CWV/CrUX field data uses), and optionally diffs TTFB against a `Server-Timing` header your origin/CDN adds — to answer "is the gap between what my app reports and what the browser sees a network/edge problem or an origin problem?"

No framework, no build step, no bundler — plain ESM throughout. `chronoscope.mjs` is a thin entry point/orchestrator; everything reusable lives in `src/` as plain `import`/`export`, resolved natively by Node. Everything else in the repo (besides `src/` and `test/`) is config or output.

## File layout

- **`chronoscope.mjs`** — entry point. Owns the bootstrap sequence (`--help` → unknown-flag alert → config load → `SITE`/`ALL_TARGETS` derived) and `main()` (the run loop, SIGINT/SIGTERM handling, pause/resume state). Deliberately not split further — it's the one place that legitimately needs to coordinate everything below.
- **`src/constants.mjs`** — `NETWORK_PRESETS`, `MOBILE_PRESETS`, `TOOL_DEFAULTS`, `NOTABLE_GAPS_TARGET`, etc. Pure static data, safe to import from anywhere.
- **`src/help.mjs`** — `HELP_TEXT`, `KNOWN_FLAGS`.
- **`src/config.mjs`** — `loadSiteConfig`, `flattenTestUrls`, `slugFromUrl`, `describeTargets`, `validateHeaders`, `buildSite`.
- **`src/cli.mjs`** — `parseArgs`, `resolveRuntimeConfig`.
- **`src/browser.mjs`** — `launchBrowser`, `setupPage`, `hitOnce`, `buildTaggedUA`/`toMobileUA`, `waitForManualClose`/`waitForKeypress`/`waitForDevtoolsAttach`.
- **`src/output.mjs`** — ANSI helpers, `boxTop`/`boxLine`/`boxBottom`, `renderTable`, `logRequest`, `printRunningAggregate`, `printFinalSummary`.
- **`src/summary.mjs`** — `buildSummary`.
- **`src/util.mjs`** — `nowIso`, `shortId`, `round`, `sleep`, `percentile`, `stats`.

**Every `src/` module is a pure function library — zero module-level side effects.** This is load-bearing, not a style preference: ES module `import` statements are hoisted and fully *executed* before the importing file's own top-level code runs, regardless of where the `import` line sits textually. If, say, `src/config.mjs` loaded the config file (and possibly `process.exit(1)`'d) as a side effect of merely being imported, that would run *before* `chronoscope.mjs`'s own `--help` check got a chance to execute — silently inverting "Bootstrap order matters" below. So every `src/` module only *defines* functions/constants; `chronoscope.mjs` alone decides the actual call order, exactly reproducing the sequence the original single-file script executed top-to-bottom.

One consequence: `SITE`, `ALL_TARGETS`, and `METRIC_LABEL` are no longer implicit module-level globals every function can see — they're resolved once in `chronoscope.mjs` and passed explicitly into whatever needs them (`site` as an extra parameter to `hitOnce`/`resolveRuntimeConfig`, `metricLabel`/`serverTimingMetric` into the `output.mjs` printing functions). Below, prose that refers to `SITE.x`/`METRIC_LABEL` is describing the *value*, which still works the same way at runtime — just check the File layout above for which module actually contains the function in question.

## Commands

```bash
# install (skip Playwright's bundled browser download — this tool only ever
# drives real installed Chrome via `channel: 'chrome'`, never bundled Chromium)
PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1 npm install

# run against ./latency-config.json (default path)
node chronoscope.mjs

# full CLI + config file reference
node chronoscope.mjs --help

# quick syntax check
node --check chronoscope.mjs

# end-to-end test suite (see "Test suite" below) — real Chrome, real
# subprocesses, ~60 tests, roughly 75-90s
npm test
```

There is no lint config. Correctness for anything not covered by the test suite has historically been verified by running the script live against a real site for a short burst (`--interval` set low, `--jitter=0`), sending it `SIGINT`, and inspecting the console output plus the generated `logs/requests-*.csv` / `summary-*.json` — still the way to sanity-check something the suite doesn't reach (e.g. console formatting/color, or behavior against a specific real site's quirks).

`npm start` also works but forwards no args by default; pass flags after `--` (`npm start -- --only=home`), or just call `node chronoscope.mjs` directly.

## Test suite

`test/*.test.mjs`, run via Node's built-in `node:test` (no framework dependency). Every test spawns the real `chronoscope.mjs` binary as a subprocess via `test/helpers.mjs`'s `spawnTool`/`runForHits` and asserts on its actual stdout, exit code, and the CSV/JSONL/summary.json files it writes — nothing here is mocked, deliberately, since almost every real bug in this codebase has been about end-to-end behavior (signal handling, process lifecycle, CDP interactions), not an isolated function a unit test would catch.

- **`test/server.mjs`** — a local, fully-controlled HTTP server (never a real site, and never anything from a user's own `latency-config.json`) that every test target points at. Delay, `Server-Timing` value/name, and HTTP status are all driven by query params on the request URL, so alarm scenarios (gap-only, ratio-only, combined, none) are constructed deterministically rather than depending on a real site's actual latency at test time.
- **Connection reuse is verified by a server-side TCP connection counter, not by reading `dns_ms`/`connect_ms` from the tool's own output.** Tried the obvious thing first — throttle the connection via `--network-rtt` to force a fresh handshake to take measurably longer than a reused one — and it doesn't work over loopback: wall-clock time reflects the throttle, but the Navigation Timing entries themselves (`connectStart`/`connectEnd`/`responseStart`) read near-zero regardless of whether the connection was actually fresh or reused, for reasons that didn't repay further digging. `test/server.mjs` instead counts actual `'connection'` events on the underlying `http.Server` — ground truth, independent of any Performance API quirk.
- **Every test file must snapshot `logs/` in `before()` and delete only its own new files in `after()`** (`snapshotLogFiles`/`cleanupNewLogFiles` in `test/helpers.mjs`) — every `chronoscope.mjs` invocation writes 3 files to `logs/` regardless of whether a given test reads them, and that directory is real, persistent, gitignored output the user's own real runs also write into. Forgetting this in a new test file doesn't fail anything — it just quietly leaves permanent test debris in the user's `logs/` directory, which is exactly what happened when several test files were first added without it.
- **The suite must run with `--test-concurrency=1`** (baked into the `npm test` script). Node's test runner can run separate test *files* in parallel by default; since every file shares the same physical `logs/` directory, one file's `before()` log snapshot can race against another file's subprocess writing new files at the same wall-clock moment, corrupting the snapshot-diff cleanup logic in both. Confirmed directly: running two files together without this flag non-deterministically picked up the wrong file's CSV in an assertion.
- **A test that intentionally leaves the tool "paused" mid-run (e.g. `--new-tab-on-alarm` after a first Ctrl+C) must send however many more `SIGINT`s it takes to reach a real `finalizeAndExit`, and `await` that exit, inside the test itself** — never rely on a `finally` block's `SIGKILL` to clean it up. `SIGKILL` can't be caught, so it never runs `browser.close()`; killing the Node test-harness process this way orphans the Chrome process it was still holding open. Confirmed via `ps aux | grep playwright_chromiumdev_profile` after a test run — a real, reproducible leak the first version of this pattern had.
- **This suite itself caught a real, shipped bug**: sending `SIGINT` in the narrow window between the startup banner starting to print and `launchBrowser()` resolving (Chrome takes a moment to start) crashed the process with `ReferenceError: Cannot access 'browser' before initialization` instead of shutting down gracefully — `browser` was declared via destructuring (`let { browser, ... } = await launchBrowser(...)`) after `finalizeAndExit`/the `SIGINT` handler were already registered, so a signal arriving in that window hit it while still in the temporal dead zone. Fixed by declaring `let browser;` before `finalizeAndExit` is defined and reassigning it via `({ browser, ... } = await launchBrowser(...))` afterward. Found by a test that happened to send `SIGINT` right after the "Targets" banner line — before that fix, no amount of manual live-testing had ever hit this window by chance.
- **`findTestChromeMainPid()`** (used by the dead-browser-relaunch and no-orphan-left-behind tests) matches on `--disable-blink-features=AutomationControlled` (a flag only `launchBrowser()` ever passes) plus `playwright_chromiumdev_profile-` (Playwright's own ephemeral temp profile — never the user's real Chrome data) and excludes any `--type=` helper/renderer/GPU subprocess, so it returns exactly the one main browser process a `chronoscope.mjs` invocation launched. This only works because `--test-concurrency=1` guarantees at most one such process exists at any moment during the whole suite.

## Architecture

### Config-driven, not code-driven
All site-specific identity — which URLs to hit, locale/timezone, the UA suffix, the name of the `Server-Timing` metric to compare against — lives in a JSON config file (default `./latency-config.json`, override with `--config=<path>`), not in the script. Adding a new site/brand should never require editing `chronoscope.mjs` or `src/`; see `latency-config.example.json` for the schema (also documented in full in `HELP_TEXT`, `src/help.mjs`).

### Bootstrap order matters
`--help` is checked against raw `argv` and can print and exit **before** any config file is loaded — this is deliberate, so `--help` works even with no config present yet (first-run UX). Right after that, `KNOWN_FLAGS`/`unknownFlags` catches a misspelled flag (e.g. `--reuse-connecton`) and prints a bold-red alert — also before config loading, so a typo still surfaces even if the config file *also* happens to be broken in the same run, rather than only the unrelated config error showing. `parseArgs()` itself doesn't validate flag names, only extracts whatever `--key=value` pairs are present, so without this check an unrecognized flag would be silently accepted and just do nothing. That alert hardcodes its own ANSI bold-red codes rather than importing `alarmize()` from `src/output.mjs` — not a temporal-dead-zone issue post-refactor (a static import would already be fully initialized by this point), just deliberately zero dependency on anything beyond this one bootstrap-time line, since it has to survive even a config that's completely broken. Only after both of these does `chronoscope.mjs` resolve a config path, load+validate it (`loadSiteConfig`, `src/config.mjs`), and flatten `testUrls` into a target list (`flattenTestUrls`). Reordering these steps risks making `--help`/the unknown-flag check depend on a config file existing — see "File layout" above for why every `src/` module is written to make that reordering impossible by construction.

### Two separate settings namespaces
- `TOOL_DEFAULTS` — how a *run* behaves (interval, jitter, headless/off-screen window, viewport, navigation timeout). CLI-flag-driven, identical regardless of which site you're testing.
- `SITE` — what site this run targets (locale, timezone, UA suffix, query param, custom `headers`, the `Server-Timing` metric name, alarm thresholds), resolved once at startup from the loaded config file, with `TOOL_DEFAULTS` as fallback for anything the config omits.

CLI flags can override `SITE.alarmGapMs`/`alarmGapRatio` per-run, but not locale/UA/targets/headers — those are config-only, since they're site identity, not run behavior.

### Target model
`testUrls` in config can mix three shapes per group: a single URL string, an array of URLs, or a `{name: url}` object — `flattenTestUrls` normalizes all of them into a flat `{name, group, url}` list, with a collision guard that auto-renames and warns on duplicate target names. `slugFromUrl` derives names for array entries from the URL's path *and* query string (URLs differing only by query, e.g. faceted search pages, would otherwise collide on the same path segment). `--only` filters against whatever groups/names the loaded config actually produced — there is no hardcoded target list anywhere.

### Per-request lifecycle (`hitOnce`)
1. A **fresh browser context per request** (not a fresh browser process) — separate cookie jar/cache/connection partition so each hit approximates a first-time visitor rather than reusing a warm connection (unless `--reuse-connection` is set — see below, it's the one deliberate exception). `extraHTTPHeaders: SITE.headers` is attached here too, so a config's custom headers ride along on every request from that context.
2. Optional CDP network throttle (`Network.emulateNetworkConditions`) and/or mobile device emulation (viewport/touch/`isMobile` + a derived Chrome-for-Android UA) applied to that context before navigating. If `--devtools` is active, `waitForDevtoolsAttach` polls raw CDP `Target.getTargets` for the `devtools://` target to exist (plus a short buffer) *before* navigating — DevTools attaches asynchronously, racing an immediate `page.goto()`, and the document request (the one thing worth inspecting) is gone for good if the Network panel wasn't yet recording when it fired.
3. Navigate with `waitUntil: 'domcontentloaded'`, deliberately **not** `'load'` — TTFB/DNS/connect/TLS/download all come from the main document's own Navigation Timing entry, fixed well before `load` fires, but waiting for `load` (all images/CSS/JS) can make an otherwise-instant reading fail with a timeout under throttling, for zero accuracy gain.
4. Read `performance.getEntriesByType('navigation')[0]` for the timing breakdown, and optionally find the configured `Server-Timing` entry to compute `gap_ms`/`gap_ratio` and decide `alarm` + `alarm_reason` (`'gap'`, `'ratio'`, or `'gap+ratio'` — tripped by an absolute-ms threshold OR a ratio threshold; either alone misses real cases, see the comment above `alarmGapMs` in `TOOL_DEFAULTS`).
5. In manual mode (`--manual`/`--devtools`/`--pause-on-alarm`), the `finally` block's decision to auto-close the context or leave it open for the human is made *after* step 4, since `--pause-on-alarm` needs `record.alarm` to decide — see `stayOpen` in `hitOnce`.

### Shutdown correctness (non-obvious, don't "simplify")
Playwright installs its own `SIGINT`/`SIGTERM` handler by default that kills the spawned Chrome process and calls `process.exit()` itself shortly after the signal — which used to race the app's own graceful-shutdown code. `launchBrowser()` now passes `handleSIGINT: false, handleSIGTERM: false` to `chromium.launch()` specifically to remove that race entirely: Playwright no longer reacts to either signal at all, so `main()`'s own handler is the *only* code deciding what happens, and it's free to `await browser.close()` before exiting.

This wasn't just a cleanup — it was required to make `--new-tab-on-alarm`'s pause-on-first-Ctrl+C behavior possible at all. With Playwright's own handler still active, it would have closed Chrome (and every kept-open tab) regardless of what our own handler decided to do on that same signal.

`finalizeAndExit` still does the summary build + file writes (`fs.writeFileSync`) synchronously before anything else — that part of the original concern doesn't disappear just because the race with Playwright is gone; a real `SIGKILL` or crash could still cut things off mid-write regardless of how graceful the rest of shutdown is. What changed is what comes *after*: closing the browser is now awaited rather than raced against a timeout. An earlier version raced `browser.close()` against a 3-second `sleep()` as a safety net against a hung/zombie browser — that sounds reasonable but isn't: real Chrome shutdown can itself take a few seconds (see the "dead browser connection" note below), so the race would sometimes fire `process.exit()` *before* `browser.close()` actually finished, silently orphaning the Chrome process — caught by checking `ps aux` for lingering `playwright_chromiumdev_profile-*` processes after a test run. The actual safety net doesn't need an artificial timer: `shuttingDown` is set to `true` before the `await`, so a second `SIGINT`/`SIGTERM` arriving while a slow close is still in flight hits the `if (shuttingDown)` branch at the top of `finalizeAndExit` and exits immediately, no matter what `browser.close()` is doing.

### Visibility modes: headless by default, and why the manual-mode plumbing is non-trivial
Headless (`TOOL_DEFAULTS.headless = true`) is the default specifically so a run never steals window focus or shuffles other windows — macOS activates an app on launch regardless of window position, so the old "off-screen headed window" approach didn't actually solve that. The one thing headless changes that matters: Chrome's own UA string says `HeadlessChrome` even in "new" headless mode, an instant bot-detection tell. Since every real navigation already overrides the UA explicitly via the `userAgent` context option (see `buildTaggedUA`), `launchBrowser()` just strips the `HeadlessChrome/` token from the *probed* UA string before anything uses it — the wire UA stays clean regardless of headless state, so there's no accuracy tradeoff.

`--headed` / `--manual` / `--devtools` / `--pause-on-alarm` all run a real, visible window instead (each implies the ones before it: `--pause-on-alarm` → `--manual` → `--headed`). Several things worth knowing if you touch this code:
- **Window sizing is screen-adaptive, not a fixed guess.** `launchBrowser()` probes `window.screen.availWidth/availHeight` (same probe page used for the UA), then sizes `headedViewport` to fit within it minus a margin reserved for Chrome's own title bar/tab strip/toolbar (measured empirically at ~80px; the margin is 120px for safety, with no fixed upper cap — an earlier version also capped this at a flat 1280x800 "to be safe," which instead made the window look tiny on any screen with a larger logical resolution than that, i.e. most modern laptops).
- **That probe context must pass `viewport: null`.** Without it, Playwright applies its own default device-metrics override (a fixed 1280x720 emulated viewport) to the context, and Chrome's `window.screen.*` properties then report *that emulated size* back as if it were the real display — completely independent of the actual screen, and identical on every run regardless of the real resolution. `viewport: null` disables the override so the probe reflects the real host window.
- **A real off-screen window is not achievable on macOS.** `--headed` (without `--manual`) pushes the window to `--window-position=10000,0` to stay out of your way, but macOS's window manager won't let a standard, focusable app window have zero overlap with any display — it snaps back to keep some minimum portion reachable, so it ends up partially visible regardless of how far off you push it. This is expected, not a bug to keep chasing; `--manual`/`--devtools` never try to hide the window in the first place (you need to see and click on it), so they're unaffected.
- **A dead browser connection during manual pauses is expected, not exceptional.** Real Chrome's shutdown (updater/crash-reporter cleanup subprocesses, etc.) can leave it in a zombie state for several seconds after its last window closes — not usable, but not yet reporting `disconnected` either. `main()`'s loop handles this with a one-shot retry: if a request fails against a browser that's dead (`!browser.isConnected()` or the error message itself says so), it relaunches and redoes that exact request before recording anything, so quitting Chrome mid-manual-session costs zero spurious error rows. `waitForManualClose` resolves on whichever of `page.on('close')` or `browser.on('disconnected')` fires first, with both listeners explicitly cleaned up either way to avoid a slow leak across a long manual session.

`--pause-on-alarm` reuses all of the above but only keeps the context open when `record.alarm` is true — everything else auto-closes and proceeds on the normal timed interval, same as a fully automated run.

### `--no-js`: document-level timing with scripts disabled
Sets `javaScriptEnabled: false` on the context. The non-obvious risk this could have broken: `hitOnce` reads timing via `page.evaluate(() => performance.getEntriesByType('navigation')...)`, and `Emulation.setScriptExecutionDisabled` (what `javaScriptEnabled: false` maps to under the hood) sounds like it should block that too. Verified empirically that it doesn't — Playwright's `evaluate()` runs in a context Chrome treats separately from the page's own disabled script execution, so timing extraction is unaffected. `page.title()` also still works (reads static DOM, no script needed).

### `--reuse-connection`: isolating connection-setup cost from origin response time
Every normal hit deliberately never reuses a connection (see "fresh browser context per request" above) — which means any one-time cost sitting between you and the origin (DNS, TCP, a VPN tunnel's per-connection tax, a corporate proxy) gets paid on *every single hit*, indistinguishable in the numbers from the origin itself being slow. This flag exists because that's exactly the failure mode that came up in practice: an internal endpoint reachable only over VPN consistently alarmed through Chronoscope but looked fine on a manual hard-reload — the manual reload was silently reusing an already-warm connection that a fresh-context hit never gets to.

`--reuse-connection` keeps one page/context alive per target for the entire run and calls `page.goto()` again with a fresh `SITE.queryParam` id on that same page, instead of opening a new context per hit — same TCP connection, so only whichever hit happens first on that target's page pays full connection setup.

- Works with any number of targets — see `persistentByTarget` below. Each target gets its own dedicated page, so it's impossible for one target's connection reuse to be disturbed by another target being hit in between (confirmed empirically: interleaving two other targets between repeat hits to a third still shows `dns=0ms connect=0ms tls=0ms` on the third's second hit).
- Also applies Empty-Cache-and-Hard-Reload semantics — `Network.clearBrowserCache` + `Network.setCacheDisabled(true)` via CDP, sent once at page creation — specifically so a cache hit can never be mistaken for connection reuse; the *only* thing intentionally carried across hits is the TCP connection itself.
- `main()` holds live `{ context, page }` pairs in a `persistentByTarget` Map, keyed by `target.name`, across loop iterations, and hands the entry for the *current* target into `hitOnce`, which skips context/page creation entirely when given one (`if (persistent) { ({ context, page } = persistent) } else { ...create as normal... }`) — `hitOnce` itself has no idea whether it's the only target or one of several; it just uses whatever it's handed. Devtools-attach and CDP throttle/cache-disable setup only happen once per target, on that target's first hit, via a shared `setupPage()` helper (see below). `hitOnce`'s own `stayOpen` is unconditionally `true` under this flag (`stayOpen = reuseConnection || (manual && ...)`), so it never closes the context itself; only `main()` does, and only by clearing the whole `persistentByTarget` map when the browser itself gets relaunched after a dead connection — a dead browser takes every target's context down with it, not just the one being hit at that moment.
- Combines with `--manual`/`--devtools`/`--pause-on-alarm`, using the exact same `shouldPause = manual && (!pauseOnAlarm || record.alarm)` condition `main()` already used for the non-reuse case — what differs is only the *mechanism* for resuming, since there's no window-close to wait on when the page is never supposed to close: `waitForKeypress()` (blocks on a single stdin `'data'` event) instead of `waitForManualClose()`. This needs a real interactive terminal attached to stdin — in a non-TTY context (piped, backgrounded, some automation wrapper) it hangs forever waiting for input that will never arrive. `Ctrl+C` still works regardless, since `SIGINT` handling is registered independently of stdin.

### `--new-tab-on-alarm`: unattended evidence collection instead of pausing
Requires `--reuse-connection`. Where `--pause-on-alarm` stops on every alarm and waits for a human, this doesn't pause *automatically* — the tradeoff is you're meant to come back and look later instead of watching live. On an alarming hit, `main()`'s loop leaves the just-alarmed page untouched (so its DevTools Network panel, if `--devtools` is active, keeps exactly that one request — nothing gets a chance to overwrite it) and opens a brand-new `page` in the *same* `context` via `context.newPage()`, which becomes that target's new entry in `persistentByTarget` for future hits.

A first `SIGINT` under this flag pauses instead of exiting (`paused = true` in `main()`), rather than running `finalizeAndExit` — see the SIGINT handler and the `while (paused) { await waitForKeypress(); ... }` check at the top of the target loop. This exists because the original all-or-nothing behavior was actively counterproductive here: tabs open at unpredictable moments (whenever an alarm fires) which made it hard to sit and inspect one calmly, and a single Ctrl+C used to tear down the whole browser — including every tab you were trying to preserve — the instant you tried to stop. Now a first Ctrl+C freezes the automated loop entirely (an in-flight hit still finishes normally; only the *next* one is held back) while leaving Chrome and every kept-open tab untouched; a resume keypress picks the loop back up, and a second Ctrl+C while already paused falls through to a real `finalizeAndExit`. This is the specific reason Playwright's own signal handling had to be disabled (see "Shutdown correctness" above) — it would otherwise close Chrome out from under this on the very first Ctrl+C regardless of what `main()` decided.

Same context, not a new one, deliberately — Chrome's connection pooling is per-context, not per-page, so the new tab still shares the already-warmed-up connection the whole run has been building on. Confirmed empirically: the hit immediately after a tab-keep still shows `dns=0ms connect=0ms tls=0ms`.

The new tab needs the exact same one-time setup a freshly-created persistent page gets (devtools attach, CDP throttle, cache-disable) — factored into `setupPage(context, page, devtools, networkProfile, reuseConnection)` specifically so this code path and `hitOnce`'s initial-creation branch can't drift out of sync with each other. `newTabCount` (in `main()`) is just a running counter for the console message, reset to `0` alongside `persistentByTarget.clear()` on a browser relaunch, since a dead Chrome takes every kept-open tab down with it too. Deliberately no cap on tab count — each kept tab is real Chrome memory, so a long unattended run with frequent alarms is a real resource consideration, not hypothetical; the running count in the console message is the only guardrail, not an enforced limit.

**`--devtools` doesn't imply pausing here** (the one exception to "popping DevTools open... implies `--manual`" above): `manual` is computed as `Boolean(cli.manual || (devtools && !newTabOnAlarm) || pauseOnAlarm)`. Without that carve-out, `--devtools --new-tab-on-alarm` would force `shouldPause` true on literally every hit (`manual && !pauseOnAlarm`), turning "run unattended and collect evidence" back into "stop and wait for Enter every single time" — the exact opposite of the flag's purpose, and a real bug caught by actually running the combo live rather than reasoning about it in the abstract. `devtools` itself is untouched by this — it still attaches DevTools to every page (initial and post-alarm) via `setupPage`; only its *implication for pausing* is suppressed. Passing `--manual` or `--pause-on-alarm` explicitly alongside `--new-tab-on-alarm` still forces pausing, since those are deliberate asks rather than a side effect of wanting DevTools open.

### Network throttling and mobile emulation
`--network=<preset>` calls the same CDP method (`Network.emulateNetworkConditions`) Chrome DevTools' own Network tab throttling uses, so it affects the *whole* request lifecycle (connect/TLS/response/download), not a delay tacked onto the end. `NETWORK_PRESETS`' `slow-4g`/`slow-3g` numbers are the long-standing Lighthouse/WebPageTest mobile defaults, not whatever Chrome's own DevTools UI currently ships — those have shifted across Chrome versions.

`--mobile`/`--device=<name>` emulate a real Android device's viewport/touch/pixel-ratio via the same CDP mechanism as DevTools' device toolbar. Android, not iPhone: driving real Chrome under an iPhone UA would claim Safari/WebKit while the engine underneath is still Chromium — a mismatch real bot detection can key on. The UA itself is never hardcoded; `toMobileUA` rewrites the *actually probed* desktop UA into the Chrome-for-Android format, keeping the real `Chrome/<version>` token intact so it can't drift stale relative to whatever Chrome is actually installed.

### Output
Every run writes three files into `logs/`, all sharing one `runId`: `requests-*.csv` (flat per-hit rows — includes `network_profile`, `device_profile`, `alarm`, `alarm_reason` alongside the timing breakdown, for spreadsheet pivoting), `requests-*.jsonl` (one JSON object per line, full detail including the raw `server_timing` array), and `summary-*.json` (aggregate stats + `notableGaps`, written once on shutdown). Each hit's unique id is embedded as a query param (`SITE.queryParam`, default `latencytest`) on the actual URL requested, so a specific hit can be cross-referenced in the origin's own access/app logs.

`notableGaps` (in `buildSummary`) is every alarming hit, not the N largest gaps — alarm is OR-triggered (gap OR ratio), so a ratio-triggered alarm can have a smaller absolute gap than some hit that never alarmed at all; sorting by raw `gap_ms` and taking the top 5 could silently drop a real alarm in favor of a bigger-but-fine one. Below `NOTABLE_GAPS_TARGET` (5) alarms, it pads with the next-worst non-alarming hits so there's still something to compare against; at or above it, every alarm is shown with no cap.

Padding can come up short of `NOTABLE_GAPS_TARGET` for a reason that looks like a bug but isn't: padding only has candidates from `withServerTimingAll` (hits that actually returned the configured `Server-Timing` metric), so a target with no `serverTimingMetric` data (e.g. a third-party comparison URL) contributes zero non-alarming candidates regardless of how many hits it had. `buildSummary` exposes `eligibleNonAlarmingCount` (the size of that candidate pool) specifically so `printFinalSummary` can tell "padded short because there weren't enough alarms" apart from "padded short because there was nothing eligible to pad with" — the latter prints an explicit caveat line under the section title rather than silently showing fewer than 5 entries with no explanation.

### Console output formatting
Three distinct visual registers, used consistently everywhere:
- **Static run config** (`boxTop`/`boxLine`/`boxBottom`) — the startup banner and the final summary's header both use this bordered "info panel" look. Left-bordered only, no fixed right edge: a box that has to align on both sides breaks the moment a value is longer than expected (the User-Agent line is ~140 chars); terminals wrap long lines fine on their own, so there's nothing to gain by fighting that.
- **Live per-hit facts** (`logRequest`) — three lines per hit: an unstyled headline (identity — never bolded/reddened even when alarming, since the *fact of this hit* isn't what's alarming), a metrics line (`ttfb :: value` — bold on the **value** only, not the label, `|` separating the two independently-measured numbers from the derived gap), and a `↳`-prefixed breakdown line (DNS/connect/TLS/wait/download). `buildMetricsLine`/`buildBreakdownLine` are shared between this and the final summary's `notableGaps` list specifically so an entry looks identical whether you're watching it scroll by live or reading it after the fact — don't let these two call sites drift into similar-but-not-quite-matching formats again.
- **Computed/secondary data** (`printRunningAggregate`, the DNS/connect/TLS/wait table in the final summary) — dimmed (`dimize`/`boldDim`), with only the metric *names* bolded (opposite of the per-hit metrics line, which bolds the *value*) so a label still anchors the eye while everything around it reads as background. `fmtMs` deliberately does **not** pad values to a fixed width — an earlier version did, and it made columns look *less* even, not more, since only some values happened to need the extra leading space to reach a given width.

One non-obvious constraint behind all of this: ANSI SGR codes aren't nested/scoped, just a flat stream of state changes. Wrapping an already-`boldize()`d segment inside an outer `alarmize()`/`dimize()` call causes the inner segment's own reset to cancel the outer style for everything after it. The fix used throughout is to never nest styling calls — either build a line from small self-contained segments (each with its own open+reset, safe to concatenate), or decide once per line which single style (if any) wraps the whole already-plain-text line.

For the "Overall + per-target" and "DNS/connect/TLS/wait" tables in the final summary, `renderTable` computes column widths from the *raw* (unstyled) content — same reasoning as `boxTop`'s dash-count math — then applies `headerStyle` per-cell (self-contained) and `rowStyle` to the whole already-plain joined line (safe only because data cells have no ANSI of their own to conflict with it).
